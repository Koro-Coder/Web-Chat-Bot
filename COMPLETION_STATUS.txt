🏗️ ARCHITECTURE PRINCIPLES
═══════════════════════════════════════════════════════════════════════

1. GENERICITY
   No business-specific concepts (search, LLM, forms, etc.)
   Protocol works with any bot implementation

2. IMMUTABILITY
   All models are Java 21 records
   Thread-safe by design
   Value semantics (equality by content)

3. SESSION OPACITY
   SDK never interprets client session state
   Server session is opaque to client
   Application defines state structure

4. EXTENSIBILITY
   Opaque payloads support any structure
   Metadata for custom fields
   Custom activity types via CUSTOM enum

5. TRACEABILITY
   Correlation IDs for end-to-end tracing
   Request/response linking
   Event tracing capabilities

6. SCALABILITY
   Stateless protocol layer
   Opaque session tokens (distributed)
   Asynchronous event processing

🔧 PRE-FREEZE PROTOCOL ENHANCEMENTS
═══════════════════════════════════════════════════════════════════════

Added ConversationExecutionContext Interface (v1.1.0):

Purpose:
   Framework-managed context supplied to handlers during execution
   Enables future framework extensibility without protocol changes
   Contains sessions, attributes, and operational context

Value:
   ✓ Future-proofs handler signatures
   ✓ Avoids breaking changes when adding framework context
   ✓ Supports feature flags, config, and helper objects
   ✓ Maintains protocol immutability and cleanliness

Interface Definition:
   public interface ConversationExecutionContext {
       ClientSession clientSession();
       ServerSessionReference serverSession();
       Map<String, Object> attributes();
   }

Usage Pattern (Framework will implement):
   ActivityResponse handle(
       ActivityRequest request,
       ConversationExecutionContext context
   );

This allows handlers to access framework-managed state without
encoding business logic into the protocol layer. The context is
supplied by the framework at invocation time.
